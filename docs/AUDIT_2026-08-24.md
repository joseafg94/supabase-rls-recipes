## Current platform findings

1. Grants and RLS are separate authorization layers. New-project defaults began changing on May 30, 2026 so new `public` tables are not automatically exposed; enforcement for existing projects is scheduled for October 30, 2026. Recipes must declare and test grants instead of depending on project defaults. Source: [Data API exposure breaking change](https://supabase.com/changelog/45329-breaking-change-tables-not-exposed-to-data-and-graphql-api-automatically).
2. Supabase currently recommends one explicit policy per operation, role-qualified policies, paired `USING`/`WITH CHECK` for updates, and tests in the same change as grants and policies. Source: [Supabase RLS guide](https://supabase.com/docs/guides/database/postgres/row-level-security).
3. PostgreSQL combines applicable permissive policies with `OR` and restrictive policies with `AND`; table owners and `BYPASSRLS` roles normally bypass RLS. Tests must therefore use non-owner application roles. Source: [PostgreSQL row security](https://www.postgresql.org/docs/current/ddl-rowsecurity.html).
4. Storage upload needs `INSERT`; upsert also needs `SELECT` and `UPDATE`. The planned Storage matrix already covers these distinct paths. Source: [Storage access control](https://supabase.com/docs/guides/storage/security/access-control).
5. The CLI's native database test path is pgTAP through `supabase test db`, with tests conventionally stored under `supabase/tests`. Source: [Supabase testing and linting](https://supabase.com/docs/guides/local-development/cli/testing-and-linting).

No reviewed planning claim contradicts these sources. Version-sensitive claims must be checked again when their implementation phase starts.

## Decisions for phase 01

- Use the stable Supabase CLI as an exact-version npm development dependency and commit `package-lock.json`; discover the version and command flags from the registry and installed `--help` during phase 01.
- Use the CLI-managed local stack only. Do not link or authenticate to a hosted project.
- Use native pgTAP via `supabase test db` as the initial SQL test runner; add no third-party test-helper package until repetition proves it necessary.
- Keep deterministic fictional UUIDs in seeds/tests and execute app-user assertions as `anon` or `authenticated`, never as database owner.
- Treat explicit grants, RLS state, policies, and supporting indexes as catalog assertions in addition to behavioral tests.
- Keep recipe SQL outside global migrations and make the harness apply one independent recipe fixture to clean local state; phase 01 should prove this lifecycle with a non-domain smoke fixture before phase 02.
- Run `supabase db lint` and pgTAP locally; defer GitHub Actions to phase 06 as already scoped.
